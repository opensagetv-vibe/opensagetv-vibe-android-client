## Four 180-second watchdogs

All four occurred on Media3-family PUSH **debug-local player seeks**:

- `media3__push__hardware / absolute_seek` — 180969 ms
- `media3__push__hardware / seek_forward` — 180825 ms
- `gsyplayer__push__hardware__gsy_auto / absolute_seek` — 180727 ms
- `gsyplayer__push__hardware__gsy_media3 / absolute_seek` — 181106 ms

The trap sequence is consistently:

`backend_seek_invoke -> position_discontinuity_1 -> playback_state_2 -> is_playing_false -> backend_seek_return`

No `first_video_frame` or return to READY follows. This is strong evidence that a direct local seek can strand Media3 in BUFFERING when SageTV owns a PUSH stream. It does **not** prove that normal SageTV server-driven PUSH seeking is broken.

Normal PUSH Comskip on the same Media3-family backends follows the production-style sequence:

`server_flush_command -> flush_reprepare_before -> server_anchor_set/position_discontinuity -> flush_reprepare_after -> first_video_frame -> playback_state_3 -> is_playing_true`

and recovers in roughly 3.0–3.4 seconds.

Action: keep the direct PUSH seek as a backend-isolation stress diagnostic, but do not treat it as equivalent to the normal SageTV-owned PUSH seek path. A future harness refactor should distinguish these scopes explicitly.

## Media3 Pull large-Comskip delay

The repeatable ~33 second delays are real Android/Media3 output delays, not host-polling artifacts. Event traps show `server_seek_command` and `backend_seek_invoke` immediately, then the first post-seek video frame only about 33 seconds later.

Representative native Media3 Pull Comskip-right:

- recovery: 33735 ms
- data-source opens: +2
- open wait: +49 ms
- network reads: +191
- requested/received: +50,069,504 bytes
- network read wait: +5,180 ms
- network errors: 0
- video queued input increases by roughly 1,300 samples before the first post-seek frame

GSY Auto and GSY Media3 show the same ~191 reads / ~50 MB pattern on their ~33 second Pull Comskip-right cases. Network wait accounts for only a fraction of total recovery, so the leading investigation area is Media3 progressive MPEG-TS seek/extractor/load behavior, not the SageTV socket alone.

Current code already uses:

- `SeekParameters.CLOSEST_SYNC`
- a Pull-only TS PCR timestamp search window of `TsExtractor.DEFAULT_TIMESTAMP_SEARCH_BYTES * 8`
- Pull load-control durations of 5 s min / 20 s max / 0.5 s playback / 1 s rebuffer

Do not change these blindly. v0.5.64 adds 5/15/30-second live state + crash/process probes so the next run will show data-source and player progress at each point. After that, controlled A/B experiments can test an explicit Media3 Pull target-buffer size and/or a smaller TS timestamp search window one variable at a time.

## GSY/System

### Pull

The trap shows `server_play_command` followed about 150 ms later by `player_error`, then the backend is released and SageTV shows `AskToDeleteRecording`. v0.5.63 did not preserve Android MediaPlayer's `what`/`extra` values in the event name.

v0.5.64 changes the trap to `player_error_<what>_<extra>` and also traps setup/surface-prepare exception classes. The next run should identify the actual Android MediaPlayer error without depending solely on external logcat.

### Push

The Android `MediaPlayer` object exists but never reaches ready/video-size state. The startup sequence includes server pause/flush but no successful media recovery. The PUSH bridge is also architecturally questionable because Android `MediaDataSource.readAt(position, ...)` is a random-access contract while `PushBufferDataSource` is a sequential circular stream and ignores the requested read offset. Do not attempt a behavioral rewrite until the enriched error traps and crash milestones are collected.

## v0.5.64 diagnostic changes driven by this review

- Live crash/process probes at 5 s, 15 s, and 30 s during every post-action recovery wait.
- The startup playback wait also probes at 5/15/30 s.
- New Dev-package crash signatures or process death/restart terminate the wait early as `PLAYER_CRASHED` / `STARTUP_PLAYER_CRASHED`.
- Milestone records include player state, A/V counters, Pull I/O counters, latest event trap, process/PID state, and compact crash signatures.
- Existing crash buffer contents are fingerprinted at baseline; unrelated crash-buffer changes do not count as a new Dev-app crash.
- GSY/System playback startup failure is classified as media/backend failure, not infrastructure.
- Player error traps now carry Media3/Exo error-code names and IJK/System integer error codes.
- Exo/Media3 Push flush/reprepare exceptions are no longer silently swallowed; they are logged and trapped.
