# Matrix Review — 20260828_002208 issues-only run

## Scope

This report was an issues-only rerun derived from `20260827_232446_player_full_matrix.json`.
It selected 9 hardware Push/Pull configurations. The run reported 2 normal recoveries,
5 slow recoveries, 7 watchdog expirations, 2 infrastructure failures, and no player crashes.

## Findings used for v0.5.66

### 1. Issue checks must be isolated

The report proved that a failed/slow issue check can contaminate the next operation in the
same configuration. In particular, GSY legacy Exo Pull Comskip RIGHT watchdoged, then the
restart before Comskip LEFT failed to establish healthy playback and LEFT was labeled
`INFRA_ERROR`.

v0.5.66 changes issue-only execution so every selected operation gets its own full clean
playback session: clean stop -> config -> connect -> Search -> recording startup -> operation.
The per-operation startup is saved under `checkStartups`. A playback failure during that
preparation is classified as `STARTUP_PLAYBACK_FAILED` / `STARTUP_PLAYER_CRASHED`, not as
MCP infrastructure failure.

Full-matrix mode keeps the existing shared-case-session behavior.

### 2. Media3 Pull TS search experiment

Native Media3 Pull and the GSY Media3/Auto wrappers still show repeatable ~33-34 second
large Comskip recovery. The player reaches the requested timeline and remains READY/BUFFERING
without an exception or process crash until a new frame eventually renders.

Earlier exact-event/Pull-I/O runs showed roughly 50 MB of datasource scanning during the
long seek while cumulative socket wait accounted for only a minority of the wall time.
The existing 8x MPEG-TS timestamp search window is therefore the first controlled variable.

v0.5.66 changes only:

`PULL_TS_TIMESTAMP_SEARCH_MULTIPLIER = 8` -> `4`

The following stay unchanged so the result is attributable:

- constant-bitrate seeking remains enabled
- `SeekParameters.CLOSEST_SYNC` remains enabled
- Pull datasource read size remains unchanged
- Media3 LoadControl values remain unchanged
- Push behavior remains unchanged

Acceptance test: rerun isolated Media3 Pull / GSY Auto Pull / GSY Media3 Pull issue cases.
Keep 4x only if large Comskip recovery improves without reintroducing seek-to-zero failure.
Otherwise revert to 8x before testing a second variable.

## Deliberately not changed

- Media3 Push local-seek behavior: still intermittent/stalling, but normal server-driven
  FLUSH/anchor recovery works. Do not rewrite this path until a genuine server-originated
  Push seek sequence is captured.
- GSY System: startup remains a separate Android MediaPlayer problem and requires its own
  datasource/platform investigation.
- GSY legacy Exo playback code: the latest watchdog conflicts with earlier ~6-10 second
  recovery results; isolate and rerun before changing Android code.
