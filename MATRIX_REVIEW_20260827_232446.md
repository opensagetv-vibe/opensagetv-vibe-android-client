## 1. Media3-family PUSH local-seek watchdogs

All six watchdogs are the same pattern:

- native Media3 PUSH: absolute seek, +10 s, -10 s
- GSY Media3 PUSH: absolute seek, +10 s, -10 s

The exact-event trap reaches `backend_seek_invoke`, seek discontinuity, BUFFERING, `is_playing_false`, and `backend_seek_return`, then no further first-frame/READY/playing callback appears. A/V counters stop. No process crash or player error is reported.

By contrast, real server-driven PUSH Comskip follows `server_flush_command -> flush_reprepare -> server_anchor_set -> first_video_frame -> READY -> is_playing_true` and normally recovers in a few seconds.

### Recommendation

Do **not** tune decoder buffers to address these watchdogs. First isolate PUSH seek ownership. `Media3MediaPlayerImpl.seek()` currently calls `player.seekTo()` even in PUSH mode, although the working PUSH path is server rebase/FLUSH. A controlled production experiment should suppress local `player.seekTo()` in PUSH and rely on the next SageTV FLUSH/anchor. Before making that permanent, add one focused server-originated `MEDIACMD_SEEK` PUSH test to confirm the server always accompanies a PUSH seek with a stream rebase.

The debug matrix itself should continue labeling its direct local PUSH seek as a stress/diagnostic path rather than proof that normal SageTV PUSH seek is broken.

## 2. Media3 Pull large-marker Comskip delay

The strongest repeatable performance signature is in Media3 Pull and GSY engines that delegate to Media3. Each ~33 s Comskip event adds exactly **50,069,504 bytes**, which is **191 x 256 KiB** network reads. The network-wait portion is only roughly 4.5-6.3 seconds. At 15 s and 30 s the player is still in BUFFERING even though the Pull read counters have already stopped changing.

This means the majority of the delay is not simply waiting on the SageTV socket. The delay is inside the Media3 progressive/extractor/seek pipeline after the data has been fetched.

Current Media3 Pull tuning includes:

- `TsExtractor.DEFAULT_TIMESTAMP_SEARCH_BYTES * 8`
- constant-bitrate seeking enabled
- `SeekParameters.CLOSEST_SYNC`
- custom Pull LoadControl (5 s min / 20 s max / 500 ms seek / 1 s rebuffer)

### Recommended controlled experiments

Change one variable at a time and use `--issues-only` for the rerun:

1. **Timestamp search 8x -> 4x** first. Keep CBR seeking, CLOSEST_SYNC, LoadControl and 256 KiB network buffer unchanged. This directly tests the most obvious seek-scan multiplier while preserving the v0.5.8 fix direction.
2. If seek correctness remains acceptable but recovery is still ~33 s, try **8x search with constant-bitrate seeking disabled**.
3. If the read burst remains exactly ~50 MB, instrument Media3 `DataSpec.position/length` on each open and record seek-map/extractor callbacks. The fixed 191-read signature is more important than changing the 256 KiB network buffer again; the prior 1 MiB experiment already failed to solve latency.
4. Only after extractor experiments, compare the custom LoadControl against Media3 defaults. The current 500 ms seek threshold is already lower than current Media3's documented default 1000 ms, so LoadControl is not the first suspect.

Do not change timestamp search, CBR seeking, and LoadControl together; that would make a passing/failing device result impossible to attribute.

## 3. Legacy Exo Pull slow Comskip

Legacy Exo Pull and GSY legacy-Exo recover around 6-10 s, much better than Media3's ~33 s but still above the 5 s warning threshold. They share much of the same Pull extractor policy, so any successful timestamp-search experiment should be evaluated on both implementations. Do not assume the Media3-specific fix should be copied to Legacy Exo until its own focused result improves.

## 4. GSY/System startup failure

Pull reports Android MediaPlayer `what=1`, `extra=-2147483648`, i.e. a generic MediaPlayer error with a low-level system error extra. The failure occurs before `player_prepared` and before renderer counters exist. PUSH creates an `android.media.MediaPlayer` and a `SagePushMediaDataSource`, but also never reaches prepared playback.

### Recommendation

Treat System as a separate compatibility backend, not a Media3 recovery problem. Add counters/traps directly to `SagePullMediaDataSource` and `SagePushMediaDataSource` (`readAt` calls, requested positions/sizes, bytes returned, `getSize` calls, first IOException). If the first few reads look valid but MediaPlayer still reports the same low-level system error, test Android MediaPlayer with a short local MPEG-TS file of the same MPEG-2/AC3 format. That cleanly separates container/codec support from the custom `MediaDataSource` bridge.

If local-file playback succeeds but `MediaDataSource` fails, refactor the System backend around a local HTTP/pipe bridge or another platform-supported seekable source rather than continuing to harden the custom random-access bridge blindly. AUTO already selects Media3, so System can remain experimental while this is isolated.

## 5. Refactoring recommendation

Exo2 and Media3 currently duplicate large amounts of SageTV-specific seek, flush/reprepare, Pull extractor, LoadControl, and debug-trap logic. Do not merge the player classes yet, but extract small policy/config helpers after the next experiment:

- `SageTvPullExtractorPolicy` for timestamp-search/CBR/seek-parameter creation
- `SageTvPullBufferPolicy` for LoadControl constants
- one common PUSH-rebase helper contract/documentation for FLUSH + anchor semantics

This will make one-variable A/B experiments safer without hiding backend-specific behavior.
